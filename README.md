# Quick & Light Animation Format

QLA is a small streaming animation format designed primarily for resource-constrained embedded systems.

It uses the [QLI codec](https://github.com/gega/qli) to encode rectangular regions of each frame. QLA assumes that the previously rendered display contents remain available while subsequent frames are decoded. This matches displays such as the ST7789 family, where only changed rectangular regions need to be transferred again.

The design is intentionally asymmetric: encoding and frame analysis are expected to run on a PC, while the decoder is intended for small embedded MCUs.

---

## Features

* **Streaming-friendly** - animation data can be supplied in small chunks
* **Optimized for embedded MCUs** - particularly suitable for SPI displays such as ST7789
* **Asymmetric design** - complex frame analysis is performed by the encoder, while the decoder remains small
* **No heap allocation in the decoder** - decoder state is fully caller-owned
* **Minimal decoder RAM footprint**
* **Partial output decoding** - output buffers can be much smaller than a frame or rectangle
* **Dirty rectangle encoding** - subsequent frames update only changed regions
* **Per-frame delays** - every frame carries its own delay in milliseconds
* **Optional looping**
* **Optional invariant hole** - reserve part of the animation for application-rendered dynamic content
* **Optional embedded auxiliary/font blob** associated with the hole
* **Portable C implementation**
* **Header-only implementation**

The encoder is intended for host-side use and uses dynamic allocation while analyzing frames.

---

## File format versions

QLA uses a four-byte magic identifying the format version.

### `qla1`

Base QLA format.

Files that do not use extended features remain `qla1`, including files generated by newer encoders.

### `qla2`

Adds support for the invariant hole and its associated auxiliary/font blob.

A decoder supporting `qla2` also supports `qla1`.

Using a separate magic version allows older QLA readers to reject extended files immediately instead of attempting to interpret an unsupported header.

---

## Basic file layout

A QLA file consists of:

```text
header
[optional auxiliary/font blob]
frame 0
frame 1
...
end marker
```

### Base header

The base header is 10 bytes:

```text
offset  size  description
0       4     magic: "qla1" or "qla2"
4       2     width, big endian
6       2     height, big endian
8       1     pixel format + QLA flags
9       1     QLI index configuration
```

### Hole extension

A `qla2` file using `QLAF_HOLE` adds 10 bytes:

```text
offset  size  description
10      2     hole X
12      2     hole Y
14      2     hole width
16      2     hole height
18      2     auxiliary/font blob length
```

All values are big endian.

If `font_len` is non-zero, that many opaque bytes immediately follow the QLA header.

QLA itself does not interpret the contents of this blob. It only records its size so an application can locate both the blob and the animation stream efficiently.

---

## Frames and rectangles

Each frame begins with a 16-bit delay in milliseconds.

The frame then contains one or more QLI-encoded dirty rectangles.

Rectangle coordinates use:

* 8-bit fields when both animation dimensions are at most 255
* 16-bit fields when either animation dimension exceeds 255

A zero-sized rectangle terminates the current frame.

The animation ends with the QLA end marker.

The first frame contains the complete image. Subsequent frames contain only regions which need to be updated.

---

## Invariant hole

A QLA animation can optionally reserve a rectangular region using `QLAF_HOLE`.

The first frame renders the complete image, including the hole.

For subsequent frames, the encoder guarantees that no generated dirty rectangle overlaps the hole. The application may therefore draw dynamic information there independently without later animation frames overwriting it.

Typical uses include:

* clock/time overlays
* battery or charging indicators
* status icons
* other application-controlled information

The initial contents of the hole are saved from the first frame. During encoding, subsequent source frames are normalized back to those original hole pixels before dirty rectangle analysis.

This also means that when hole support is enabled, `qla_encode_frame()` may modify the pixels inside the supplied source frame so that they match the invariant first-frame contents.

Hole support in the decoder is controlled by `QLA_HOLE`.

```c
#define QLA_HOLE 1
```

A decoder built without hole support rejects files requiring the feature.

## Decoder API

### `int qla_init_decode(struct qla_anim *qla, uint16_t width, uint16_t height, uint8_t *data, uint32_t data_size, uint8_t flags);`

Initialize a decoder directly from known animation parameters.

* **qla** - decoder context
* **width, height** - animation dimensions
* **data** - first input data chunk
* **data_size** - size of that chunk
* **flags** - QLA flags

Normally file-based users should use `qla_init_header()` instead.

---

### `int qla_init_header(struct qla_anim *qla, uint8_t *hdr, uint32_t hdr_size, uint8_t *data, uint32_t data_size);`

Initialize a decoder from a QLA file header.

* **qla** - decoder context
* **hdr** - available header bytes
* **hdr_size** - number of available header bytes
* **data** - optional first animation data chunk
* **data_size** - size of the first animation data chunk

Return value:

* `0` - initialization complete
* `< 0` - invalid or unsupported header
* `> 0` - amount of additional header bytes required

This allows the caller to first read the fixed-size base header (QLA_MIN_HEADER_LEN) and only read an extended header when necessary.

When hole support is enabled, the decoded context exposes:

```c
qla->hole_x
qla->hole_y
qla->hole_w
qla->hole_h
qla->font_len
```

---

### `void qla_new_chunk(struct qla_anim *qla, uint8_t *data, uint32_t data_size);`

Provide the next input chunk after the decoder returns `QLA_NEWCHUNK`.

QLA and the underlying QLI decoder maintain their state across chunks.

---

### `qla_status_t qla_decode(struct qla_anim *qla, uint8_t *dest, int bufsize);`

Decode the next portion of the animation.

* **qla** - decoder context
* **dest** - output pixel buffer
* **bufsize** - size of the output buffer

The output buffer may be substantially smaller than the current rectangle.

### Return value

`qla_status_t` packs the output byte count and status flags:

* **upper 24 bits** - number of decoded output bytes
* **lower 8 bits** - status flags

Use:

```c
QLA_GET_SIZE(status)
QLA_GET_STATUS(status)
```

Available status flags include:

* `QLA_NEWFRAME` - a new frame has started; `qla->delay` contains its delay
* `QLA_NEWRECT` - a new display rectangle is ready; coordinates are in `qla->rect`
* `QLA_NEWCHUNK` - more encoded input data is required
* `QLA_EOS` - end of animation
* `QLA_ERROR` - decoding error

More than one status bit may be returned at the same time.

A typical embedded decoder reacts to `QLA_NEWRECT` by configuring the display controller's output window, then sends subsequent decoded bytes directly to the display until the next rectangle or frame event.

---

## Looping

The file flag `QLAF_LOOP` indicates that an animation should restart after reaching `QLA_EOS`.

QLA does not perform file I/O itself. The application is responsible for seeking its data source back to the appropriate position and resetting the decoder using the provided rewind helpers.

---

## Encoder API

The encoder performs dirty-region analysis and is intended for host-side asset generation.

### `int qla_init_encode(struct qla_encode *qle, uint16_t width, uint16_t height, qla_buffer_release_cb_t buf_rel, uint8_t flags, qla_rect_t *hole);`

Initialize an encoder.

* **qle** - encoder context
* **width, height** - animation dimensions
* **buf_rel** - callback used when a previously retained source frame can be released
* **flags** - file flags such as `QLAF_LOOP` and `QLAF_HOLE`
* **hole** - hole rectangle when `QLAF_HOLE` is enabled, otherwise may be `NULL`

The encoder retains the previous frame while analyzing the next one, which is why the release callback is provided.

---

### `void qla_destroy_encode(struct qla_encode *qle);`

Release encoder-owned resources.

If the final retained frame has a release callback, it is released here as well.

---

### `int qla_generate_header(struct qla_encode *qle, uint8_t *data, int font_len);`

Generate the QLA file header.

* **qle** - initialized encoder context
* **data** - output buffer, at least `QLA_MAX_HEADER_LEN` bytes
* **font_len** - size of the optional auxiliary/font blob

The function returns the actual number of header bytes generated.

A base animation therefore produces a shorter header than an animation using the hole extension.

If `font_len` is non-zero, the caller writes the blob immediately after the generated header and before the first animation frame.

---

### `int qla_encode_frame(struct qla_encode *qle, uint32_t *rgb, uint16_t delay_ms, uint8_t *buf, size_t bufsize);`

Encode one frame.

* **qle** - encoder context
* **rgb** - 32-bit source RGB pixels
* **delay_ms** - frame delay in milliseconds
* **buf** - output buffer
* **bufsize** - size of the output buffer

The first frame is encoded completely.

Subsequent frames are compared with the retained previous frame and represented as QLI-encoded dirty rectangles.

To generate the end marker:

```c
qla_encode_frame(&qle, NULL, 0, buf, bufsize);
```

Always check the return value before writing the returned number of bytes.

---

## Compile-time configuration

QLA uses the pixel format configured for QLI:

```c
#define QLI_PIXEL_FORMAT QLI_PF_RGB444
#define QLA_PIXEL_FORMAT QLI_PIXEL_FORMAT
```

Hole-aware decoding is optional:

```c
#define QLA_HOLE 1
```

As with QLI, define `QLA_IMPLEMENTATION` in one translation unit to include the implementation:

```c
#define QLA_IMPLEMENTATION
#include "qla.h"
```

## Testing

`qla_hole_test.c` contains an in-memory encoder/decoder regression test for the hole feature.

The test generates synthetic frames, encodes them, then feeds the generated stream back through the real QLA and QLI decoders.

Among other things it verifies that:

* the extended header is generated and parsed correctly
* hole geometry and blob length survive header decoding
* later source frames are normalized to the first-frame hole
* dirty rectangles after the first frame never overlap the hole
* QLA/QLI decoding works with a small output buffer
* the complete generated animation reaches `QLA_EOS`

Testing both normal and extended rectangle coordinate modes is recommended, for example with dimensions below and above 256 pixels.

---

## Notes

* Always check encoder and decoder return values.
* QLA decoding is designed for streaming operation.
* Input and output buffers do not need to contain an entire frame.
* The decoder performs no file I/O and no heap allocation.
* The encoder is intentionally more complex and uses temporary host-side memory.
* QLA's optional embedded blob is opaque to QLA itself; applications are free to define their own font or auxiliary data format.
